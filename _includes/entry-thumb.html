{%- comment -%} Entry image, resolved honestly — no generated placeholder. Usage: {% include entry-thumb.html entry=page img_class="rounded-md" %} Params: entry (required, an entry page object), img_class (extra classes on the ), eager (optional; true = loading="eager" for above-the-fold cards, default lazy), fetchpriority (optional; true = fetchpriority="high" — pass it for the ONE image that is the page's LCP candidate, never for a row of them). Fallback order: explicit `thumbnail` front matter -> the first image of the first `images`-type schema field -> `thumb.jpg` when it exists on disk -> NOTHING. Callers MUST treat empty output as "this entry has no picture" and omit the media band entirely (capture the include and check for blank), per design-brief principle 5. Presentation-only front matter, like `thumbnail`/`thumbnail_alt` and deliberately not in schema.yml (it describes one picture, not the entry): thumbnail_focus a CSS object-position, default "center top" — the media band is 16:7 and the top is where a deck or a dashboard puts its title. Sizes come from picture.html, which serves AVIF/WebP variants when _data/derivatives.json has an entry for this file and falls back to the plain when it does not. width/height come from the manifest too, so neither is guessed. `sizes` is measured off the built pages, not guessed, and it takes the WIDEST box any surface gives a card — the home page's grid is roomier than the catalog's, so it sets the number above 1280 (387px) and between 1024 and 1279 (46.4vw). Below 1280 the widest single-column case is 95vw (at 639) and the widest two-column case is 46.9vw (at 1023). Under-stating `sizes` ships a blurry image; over-stating it costs a few KB, so where the two grids disagree this follows the wider one. Re-measure if either grid changes.
